**Date:** 2026-04-17
**Branch:** `feature/route-creation`
**Supersedes:** nothing (new feature area)
**Mockups:** [`2026-04-17-route-creation-mockups.html`](2026-04-17-route-creation-mockups.html)

## 1. Goal

Turn the GPX analysis tool into a general-purpose route tool that also **creates** and **edits** routes, not just analyses imported GPX files. Users gain three creation entry points, all of which converge on the existing analysis page:

- **Mode A — upload GPX** *(existing)*: drop a `.gpx` file, analyse. If the file contains `<wpt>` entries, they become the route's recipe.
- **Mode B — upload CSV**: addresses and/or GPS coordinates. CSV upload is available **at any time** — as a starting point for a new route, or as an append-to-existing-route action from within the Create page or the Analysis edit panel. Addresses are geocoded via the existing Nominatim proxy; GPS columns bypass geocoding. A Valhalla routing call produces the detailed track.
- **Mode C — click waypoints on a map**: manual drop of stops and waypoints on a Leaflet map.

All three modes produce the same artifact: a **route with a recipe**. The recipe holds the list of stops and waypoints, the routing options, and per-leg travel info. The detailed GPX (hundreds–thousands of trackpoints from Valhalla) is stored alongside so analysis works anywhere. Recipe-less routes (Mode A without `<wpt>`) remain analysable but are read-only until M6 when a lossy "extract waypoints" heuristic is added.

Modes B and C are not exclusive — any combination is valid. You can start a route by clicking three waypoints on the map, then upload a CSV to append ten cafés as stops, then drag-reorder the lot.

## 2. Core concepts

### Stops vs Waypoints

Each location in a route is one of two kinds:

- **Stop** (red octagon icon): a destination the user intends to visit. May carry a non-zero `dwell_minutes` (time spent at the stop). Contributes to the route's total time.
- **Waypoint** (cyan diamond icon): a transit point that shapes the route but is not a destination. Does not carry dwell time; used to force a path (e.g. "go via this pass").

Kind is a single-column distinction, not a separate table. A user can promote/demote a location between kinds at any time.

### Recipe

The recipe is the editable source of truth for a route:

```
route_waypoints[]   — ordered list of stops + waypoints
route_options       — profile, routing preset, costing knobs, round_trip, gradient-warn threshold, timestamps
route_legs[]        — cached Valhalla segment data (distance, time, polyline) per leg
```

### Routing preset & costing options (elevation-aware)

The app is designed for off-road / national-park / fire-trail cycling where gradient navigability matters as much as distance. Rather than a bare "bicycle / walking / car" picker, each route carries a **routing preset** plus a **costing options** JSON blob that controls how Valhalla scores edges.

Presets are UI shortcuts that set a sensible costing blob; "Custom" exposes the knobs individually:

| Preset | Profile | Key costing options |
|---|---|---|
| **Road cyclist** | `bicycle` | `bicycle_type=Road`, `avoid_bad_surfaces=0.9`, `use_hills=0.5` |
| **Gravel / MTB** | `bicycle` | `bicycle_type=Mountain`, `avoid_bad_surfaces=0.0`, `use_hills=0.6`, `private_access_penalty=100` |
| **Easy ride** | `bicycle` | `bicycle_type=Hybrid`, `use_hills=0.1`, `max_gradient_warn=6%` |
| **Hike** | `pedestrian` | `use_hills=0.7`, `use_tracks=0.9` |
| **Drive** | `auto` | defaults |
| **Custom…** | any | user-controlled sliders |

Valhalla's `use_hills` is a *soft* penalty — it prefers gentler edges but will take a 20 % climb if nothing else exists. To give "I won't ride steeper than X %" teeth, every generated route is **post-processed** against `max_gradient_warn` (optional per route): any sub-segment whose smoothed gradient exceeds the threshold gets a ⚠️ badge in the sidebar ("leg 3: 18 % over 120 m") and the offending section is outlined on the map in the steepest-band colour. The user can then drop a via-waypoint to force a detour.

National-park / fire-trail handling in v1 relies on the costing knobs: `bicycle_type=Mountain` + `avoid_bad_surfaces=0` makes fire trails *preferred*, and `private_access_penalty` controls whether permit-only tracks are considered. Hard "avoid all national parks" boundaries use Valhalla's `exclude_polygons` and are deferred to M6 because they need polygon data fetched from Overpass.

### Detailed GPX

Generated by Valhalla from the recipe. Stored on disk at `{DATA_DIR}/routes/{route_id}.gpx`. Contains both:

- `<wpt>` entries — one per `route_waypoints` row, with name + description, in route order.
- `<trk><trkseg><trkpt>` — the dense polyline from concatenated Valhalla legs.

Existing analysis logic reads the `<trk>` portion unchanged; M4's rich-GPX loader reads `<wpt>` entries to populate a recipe on import.

## 3. Architecture

### Page layout (Option C, approved)

- **Library** (existing): lists routes.
- **Create Route** (new page, `src/js/create/`): dedicated creation-focused screen. Users arrive here from the Library's "+ New Route" button, or from the CSV upload flow. Manual waypoint creation, profile/options, optimise, generate, save.
- **Analysis** (existing page, extended): now hosts an **inline Edit panel** that slides out from the right side of the map. When the panel is closed, the page looks and behaves exactly as it does today. When open, it overlays the right edge of the map and reveals the same waypoint editor used on Create. Changes are persisted by clicking "Save Changes"; "Regenerate Route" is a separate explicit action.

Both the Create page and the Edit panel share a single component: `src/js/shared/waypoint-editor.js`. Shared behaviour: ordered list, drag-to-reorder, stop/waypoint kind toggle, pin-as-start/end, dwell-time edit, per-leg info display, collapse/expand.

### Frontend module layout (new)

```
src/js/
├── analysis/            # existing — gets edit-panel.js added
│   └── edit-panel.js    # NEW: slide-out panel, wires waypoint-editor into the analysis page
├── create/              # NEW: dedicated create page
```

### Backend blueprints (new)

- `server/blueprints/api_waypoints.py`
  `GET/PUT /api/routes/<id>/waypoints` — list and full-replace
  `POST   /api/routes/<id>/waypoints` — append one
  `PATCH  /api/routes/<id>/waypoints/<wpt_id>` — update kind, name, dwell, position, pin
  `DELETE /api/routes/<id>/waypoints/<wpt_id>`

- `server/blueprints/api_routing.py`
  `POST /api/routes/<id>/generate` — runs Valhalla, returns `{gpx_url, legs: [...]}`
  `POST /api/routes/<id>/optimise`  — runs NN + 2-opt on the recipe, returns new order

- `server/blueprints/api_geocode.py`
  `GET  /api/geocode/search?q=...`     — Nominatim passthrough for autocomplete
  `POST /api/geocode/csv`              — upload CSV, returns `{job_id}`
  `GET  /api/geocode/csv/<job_id>/stream` — SSE stream of progress events, ends with `{route_id}`

### Valhalla + Nominatim

Reuse the existing proxy endpoints and config values (`VALHALLA_URL`, `NOMINATIM_URL`). Synchronous per-request for single-route generation; a background thread with SSE progress for CSV geocoding (rate-limited 1 req/s per Nominatim convention).

### Data flow — CSV import (M5)

CSV upload has two modes, distinguished by whether a `route_id` is supplied:

**New-route mode** (from Library):
```
Browser → POST /api/geocode/csv           (multipart: file + column map)
      ← 202 { job_id, route_id }          — server created a new empty route
Browser → GET  /api/geocode/csv/<job_id>/stream   (SSE)
      ← event: row  { index, status: "geocoded", lat, lon }
      ← event: done { route_id, created: 12, failed: 2 }
Browser → navigate to /route/<route_id>?edit=1
```

**Append mode** (from Create page or Analysis edit panel):
```
Browser → POST /api/geocode/csv?route_id=<id>&append=1   (multipart: file + column map)
      ← 202 { job_id, route_id: <same id>, append: true }
Browser → GET  /api/geocode/csv/<job_id>/stream   (SSE)
      ← event: row  { index, status: "geocoded", lat, lon, waypoint_id }
      ← event: done { route_id, appended: 12, failed: 2 }
Browser → stays on current page; editor reloads the waypoint list when `done` arrives
```

On the server side, rows are written into `route_waypoints` as each geocodes: `position` is assigned starting at the current max (append) or from 0 (new-route). **All CSV-imported rows default to `kind = 'stop'`** (the user explicitly called these a "CSV of stops") with `included = 1`. Failed rows are kept with `lat=NULL, lon=NULL, included=0` and a note in `description`; the user can fix them manually.

### Persistent geocoding cache

`geocode_cache (query TEXT PRIMARY KEY, lat REAL, lon REAL, display_name TEXT, created_at INTEGER)`.
Every Nominatim lookup (single or batch) consults this first; hits skip the network. Fixes the old project's in-memory-only cache.

## 4. Data model (SQL)

```sql
-- Existing, unchanged — routes table holds title, category, gpx_path, etc.

-- NEW
CREATE TABLE route_waypoints (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    route_id        INTEGER NOT NULL REFERENCES routes(id) ON DELETE CASCADE,
    position        INTEGER NOT NULL,                    -- 0-indexed order
    kind            TEXT    NOT NULL CHECK(kind IN ('stop', 'waypoint')),
    name            TEXT    NOT NULL,                    -- user-visible label
    address         TEXT,                                -- original input, if any
    lat             REAL,                                -- NULL if geocoding failed
    lon             REAL,                                -- NULL if geocoding failed
    included        INTEGER NOT NULL DEFAULT 1 CHECK(included IN (0, 1)),
    pin_role        TEXT    CHECK(pin_role IN ('start', 'end') OR pin_role IS NULL),
    dwell_minutes   INTEGER NOT NULL DEFAULT 0,          -- only meaningful for stops
    description     TEXT,                                -- free text
    UNIQUE(route_id, position)
);
CREATE INDEX idx_waypoints_route ON route_waypoints(route_id);

CREATE TABLE route_options (
    route_id          INTEGER PRIMARY KEY REFERENCES routes(id) ON DELETE CASCADE,
    profile           TEXT    NOT NULL DEFAULT 'bicycle' CHECK(profile IN ('bicycle','pedestrian','auto')),
    costing_preset    TEXT    NOT NULL DEFAULT 'hybrid' CHECK(costing_preset IN ('road','gravel-mtb','easy','hike','drive','custom','hybrid')),
    costing_options   TEXT,               -- JSON blob merged into the Valhalla costing request; see below
    round_trip        INTEGER NOT NULL DEFAULT 0 CHECK(round_trip IN (0, 1)),
    max_gradient_warn REAL,               -- NULL = no warning; else flag sub-segments whose smoothed gradient exceeds this %
    last_optimised_at INTEGER,
    last_generated_at INTEGER
);

CREATE TABLE route_legs (
    route_id        INTEGER NOT NULL REFERENCES routes(id) ON DELETE CASCADE,
    from_position   INTEGER NOT NULL,
    to_position     INTEGER NOT NULL,
    distance_m      REAL    NOT NULL,
    duration_s      REAL    NOT NULL,
    polyline        TEXT    NOT NULL,                    -- encoded polyline from Valhalla
    max_grade_pct   REAL,                                -- steepest smoothed gradient on this leg
    warnings        TEXT,                                -- JSON array of {from_m, to_m, peak_grad_pct} (M3)
    PRIMARY KEY (route_id, from_position, to_position)
);

CREATE TABLE geocode_cache (
    query         TEXT    PRIMARY KEY,
    lat           REAL,
    lon           REAL,
    display_name  TEXT,
    created_at    INTEGER NOT NULL
);
```

**Schema change discipline.** Additive only. M1 adds `route_waypoints`, `route_options`, `route_legs`; M5 adds `geocode_cache`. Extend `server/models/schema.sql` and use `CREATE TABLE IF NOT EXISTS` at app startup — existing deployments upgrade seamlessly. Existing routes (no recipe) have zero rows in `route_waypoints`, which is the signal that they're GPX-only.

**Profile naming.** Storage uses Valhalla's own codes (`bicycle`, `pedestrian`, `auto`). The UI labels them "Bike", "Walk", "Car".

**`costing_options` JSON shape.** A plain object merged directly into the `costing_options.<profile>` field of the Valhalla `/route` request. Typical shape for the Gravel / MTB preset:
```json
{
  "use_hills": 0.6,
  "bicycle_type": "Mountain",
  "avoid_bad_surfaces": 0.0,
  "use_tracks": 0.5,
  "private_access_penalty": 100
}
```
Presets are a deterministic server-side function: `preset_name → costing_options`. When the user picks Custom and changes a slider, the preset flips to `custom` and the JSON is stored verbatim. This keeps us forward-compatible with new Valhalla costing options — a new knob ships as a new JSON key without a schema migration.

### M2 — Route editing (inline Edit panel on Analysis)

**Ships:**
- `src/js/analysis/edit-panel.js` — slide-out panel on the analysis page (right edge), mounted only when recipe exists.
- Panel hosts the same `waypoint-editor` component used on Create. Tabs, collapse, drag-reorder all work.
- Drag a marker on the Leaflet map to move a waypoint — updates `lat`/`lon` in the recipe on drop.
- **Save vs Regenerate semantics.** Opening the edit panel snapshots the current recipe in memory. Edits (reorder, rename, move, add, remove) mutate the in-memory working copy only. **Save Changes** persists the working copy to `route_waypoints` / `route_options`. **Regenerate Route** persists first, then calls `/api/routes/<id>/generate` (writes `route_legs`, rewrites the GPX file) and re-renders analysis. **Discard** restores the snapshot and closes the panel.
- GPX-only routes (no recipe) show a disabled Edit button with tooltip "this route has no recipe (coming in M6)".

**Acceptance:**
- Open a recipe route from M1 → Edit button visible → click → panel slides in.
- Drag marker to new location → sidebar shows "moved — regen needed".
- Click Regenerate → Valhalla called, analysis page updates (new gradient data, new total distance).
- Save Changes persists; Discard reverts.
- UI: `test_ui_edit_panel.py` covers open/close, drag, regen, discard, disabled on GPX-only.

### M3 — Routing options, elevation-aware costing, optimisation

Central milestone. Expands the bare profile picker into the full elevation- and surface-aware routing UX that's the project's design goal.

**Ships:**
- **Routing preset dropdown** (Road cyclist / Gravel-MTB / Easy ride / Hike / Drive / Custom) in the editor options bar. Selecting a preset fills `route_options.costing_preset` and `costing_options` server-side; a new REST endpoint `GET /api/routing-presets` returns the preset → costing-options mapping so the client doesn't have to hard-code it.
- **Custom costing panel** (collapsible, under the preset dropdown) with sliders and inputs for: `use_hills`, `bicycle_type` (when profile=bicycle), `avoid_bad_surfaces`, `use_tracks` (pedestrian), `private_access_penalty`, and `max_gradient_warn`. Editing a slider flips `costing_preset` to `custom`.
- **Round-trip toggle**: if on, Valhalla request appends a return leg from last→first stop.
- **Start/end pin** checkboxes (per-waypoint in the editor; also a quick pin-as-start on hover).
- **Include/exclude** per waypoint — excluded waypoints persist in the recipe but don't participate in routing (and don't appear on the detailed GPX track). Accessed two ways:
    1. A toggle control on each sidebar list item (eye / eye-slash icon), with the row dimmed when excluded.
    2. An "Include" / "Exclude" entry in the right-click context menu on the map marker.
- **`generate` endpoint wiring.** `POST /api/routes/<id>/generate` now reads `route_options.profile` + `costing_options` and injects them into the Valhalla `/route` request body at `costing` + `costing_options.<profile>`. Also passes `elevation_interval: 10` so returned trkpts carry elevation.
- **Gradient-warning post-processor** (`server/route_postprocess.py`): after every `/generate` call, scan the returned legs' elevation samples using the same smoothing+window logic as the analysis page, flag any sub-segment whose smoothed gradient exceeds `max_gradient_warn`. Warnings are persisted alongside `route_legs` (new column `warnings TEXT` — JSON array of `{from_m, to_m, peak_grad_pct}`) and surfaced in the sidebar (⚠️ badge on the affected leg row) + highlighted on the map in the steepest-band colour.
- **"Optimise" button** runs nearest-neighbour initialisation + 2-opt local search on included waypoints, respecting pins. Cost function uses *route-network distance* from cached `route_legs` when available, falling back to haversine. New API: `POST /api/routes/<id>/optimise` returns `{ new_order: [waypoint_id, ...] }`.
- Changing `profile`, `costing_preset`, or any `costing_options` value invalidates `route_legs` and marks the route as "needs regeneration" (disabled analysis until user hits Regenerate).

**Acceptance:**
- Switch preset from Road cyclist → Gravel-MTB on a route with an unpaved cut-through → Regenerate → the new track uses the unpaved cut-through (compare returned polyline to the road-preferring version).
- Route with a forced-steep segment and `max_gradient_warn=10` → sidebar shows a ⚠️ badge on the offending leg; map highlights the over-threshold sub-segment; clearing `max_gradient_warn` removes the badge without re-hitting Valhalla.
- Exclude a waypoint via the list toggle, Regenerate → route skips it. Right-click the excluded marker → re-include via context menu.
- Pin first stop, click Optimise → order changes but pinned stop stays at index 0.
- Unit: `test_optimiser.py` with synthetic point sets (include a 2-opt-reducible case); `test_route_postprocess.py` covers the gradient-warning logic with synthetic elevation samples; `test_costing_presets.py` verifies preset → costing-options mapping.
- UI: `test_ui_options.py` — preset switching, custom panel, profile switch invalidates legs, optimise reorders, pin honoured, include toggle works from list and from context menu, gradient warning badge renders when threshold is crossed.

### M4 — Rich GPX export / import

**Ships:**
- GPX writer (`server/gpx_writer.py`) emits `<metadata>`, `<wpt>` entries (one per recipe row with name + description + `type` = "stop"|"waypoint"), then `<trk><trkseg><trkpt>` of the dense polyline.
- GPX reader (upgraded `server/gpx_parser.py`) recognises `<wpt>` entries on upload — if present, creates a recipe from them AND reads the track. `<wpt type="stop"|"waypoint">` is honoured; absence defaults to `waypoint`.
- Export endpoint `GET /api/routes/<id>/export.gpx` serves the stored GPX file directly.

**Acceptance:**
- Export a recipe route; inspect the file has both wpt and trk.
- Re-import the exported file → new route has identical recipe (waypoints list matches by lat/lon to 6 dp, kinds match).
- Unit: `test_gpx_roundtrip.py`.

### M5 — CSV upload (Mode B) — new-route *and* append-to-existing

**Ships:**
- "Upload CSV" button available from **three** places:
    1. Library page → creates a **new route**.
    2. Create Route page → **appends** to the in-progress route (useful after manually dropping a start/end and then bulk-adding cafés).
    3. Analysis page edit panel → **appends** to the saved route.
- Client: parse CSV locally (PapaParse), show column-mapping dialog, let user choose which column maps to each field (`name`, `address`, `lat`, `lon`, `description`).
- POST to `/api/geocode/csv` with the file + mapping. If a `route_id` is in the query string, server appends (does NOT create). Otherwise it creates a new route and returns `{ job_id, route_id }`.
- Imported rows default to `kind='stop'`, `included=1`, and are placed at the end of the recipe in CSV row order.
- Server worker thread: for each row, lat/lon direct if present, else Nominatim lookup (with cache). Rate-limited 1 req/s per Nominatim convention (configurable via `NOMINATIM_RATE_LIMIT_MS`).
- SSE stream `/api/geocode/csv/<job_id>/stream` emits per-row progress. On completion the client either navigates to `/route/<id>?edit=1` (new-route mode) or reloads the waypoint list in place (append mode).

**Acceptance:**
- **New-route:** upload CSV of 10 rows (mix of addresses and GPS) from Library → progress bar updates row-by-row → lands on analysis page with edit panel expanded, all 10 rows visible as stops.
- **Append to Create page:** start a route with 2 manual waypoints, upload CSV of 5 rows → editor ends up showing 7 entries; the Valhalla "Generate" button becomes clickable only once all 7 have lat/lon.
- **Append to Analysis:** open existing 4-stop route, upload CSV of 3 rows → list now shows 7 entries without leaving the page; Regenerate integrates the new stops into the drawn track.
- Failed rows (bad address) show as `included=0` with an error note in `description`; row is visible in the list so the user can fix or delete.
- Unit: `test_api_geocode.py` (Nominatim mocked, both new-route and append paths), `test_csv_import.py` (column mapping).
- UI: `test_ui_csv_upload.py` — covers all three entry points.

## 7. Non-goals (for this spec)

- Multi-user / collaboration.
- Public sharing / export beyond GPX.
- Mobile-specific UI. The existing desktop-first layout is retained; responsive improvements are a separate initiative.
- Real-time-GPS tracking.
- Turn-by-turn navigation output (Valhalla produces maneuvers; consuming them is a later piece).
- Routing over *arbitrary* user-drawn polygons as a first-class object. `exclude_polygons` is used internally for park avoidance in M6, but there's no general-purpose polygon editor.

## 8. Open questions / risks

- **Valhalla request latency.** A local Valhalla can be slow on first request (cold cache). The sync-request model accepts this but we should add a 30 s timeout and graceful error. Mitigation: spinner state + clear error on timeout.
- **Nominatim rate-limit attribution.** Self-hosted Nominatim may not need the 1 req/s delay. Keep it configurable via `NOMINATIM_RATE_LIMIT_MS` env var (default 1000 ms).
- **Valhalla DEM coverage.** The gradient-aware routing depends on the Valhalla graph being built *with* DEM elevation data. The hosted `valhalla1.openstreetmap.de` instance is built with SRTM; a self-hosted Valhalla must have `elevation` in its tile-build config. If the configured `VALHALLA_URL` responds without `elevation_interval` samples in the route reply, M3's post-processor has no gradient data to work with and must degrade gracefully (warnings disabled, UI badge explaining why). Check-on-startup: issue a tiny probe route and cache whether elevation samples came back.
- **Surface + access tag coverage in OSM.** Off-road routing quality is only as good as local OSM tagging of `highway=track`, `tracktype=*`, `surface=*`, and `access=*`. Routes through sparsely-tagged areas may give noisy results; this is a data problem we can't fix in this spec, but the `private_access_penalty` knob lets users relax restrictions manually when they know a tagged-private track is actually accessible.
- **Schema migration on an existing prod DB.** M1 is additive (all new tables + two new columns on `routes` would be avoided by using new tables only). Migration must run on first app start if needed; fail-loud on version mismatch.
- **Undo/redo.** Deferred. Discard + page refresh is the v1 story.
